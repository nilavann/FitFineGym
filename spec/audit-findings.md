# Full Application Audit — Spec vs. Implementation Findings

> **Historical record.** This review is of the old `public`-schema backend. Its `supabase/migrations/…` and `supabase/tests/…` paths name files of that backend; the old migrations are in git history (`supabase/migrations/` on `master` before the move). The live backend in `supabase/` is the `fitfine` schema.
>
> Full-app pass comparing every doc under `spec/` against the actual `frontend/` and `supabase/` implementation, done 2026-07-26. Covers Member Management, Subscription Management, Reporting, Auth, Audit Trail, Admin Data Management, Domain Model/DB Schema, and Frontend Shell/Navigation/Styling. Checklist for tracking — check items off as they're addressed (in the code, the doc, or both), same convention as [domain-model-review.md](./backend/domain-model-review.md) and [security-review-findings.md](./backend/security-review-findings.md).
>
> **Headline:** the app matches its spec unusually well. REQ-MEM-\*, REQ-LIST-\*, REQ-SUB-\*, REQ-REPORT-\*, REQ-ADMIN-002/003/004/006, and REQ-AUDIT-001 are all implemented and behave exactly as specified, including deliberately-scoped-down designs (client-only overlap warnings, deferred cancellation) that were built *as* deferred rather than half-finished. Real problems cluster in three places: one broken auth flow, one missing screen, and several spec docs that drifted behind two schema redesigns (profiles→multi-role, subscription header/line-item split) without being updated.

## Critical — real bugs

- [x] **Password reset has no completion step (REQ-AUTH-005).** The request flow was fully wired (`frontend/src/pages/LoginPage.tsx`, `SettingsPage.tsx` → `authService.resetPasswordForEmail` → `supabase.auth.resetPasswordForEmail(email, { redirectTo: '/login' })`), but there was no page handling the return trip. Supabase's client auto-detects the recovery token in the URL and silently establishes a real session; `AuthContext` then saw a valid session + active profile and redirected straight to `/`. The user was signed in without ever being prompted to set a new password.
  **Fixed:** `resetPasswordForEmail`'s `redirectTo` now points at `/reset-password`; `AuthContext` (`frontend/src/context/auth.context.tsx`) watches for Supabase's `PASSWORD_RECOVERY` auth event and exposes it as `needsPasswordReset`, cleared again on sign-out/`updatePassword()` success. `RequireAuth` and `LoginPage` both redirect an in-progress recovery session to the new `ResetPasswordPage` (`frontend/src/pages/ResetPasswordPage.tsx`), which is the only place allowed to call the new `updatePassword()` (→ `supabase.auth.updateUser({ password })`). Docs updated to match: [screens.md WSCR-13](./frontend/screens.md), [frontend/auth.md §3.1/§4.3](./frontend/auth.md), [backend/auth.md §4.3/§6](./backend/auth.md), [navigation.md](./frontend/navigation.md). Verified via `tsc --noEmit` and a full `vite build` (new page code-splits into its own chunk); the real email-round-trip path against the hosted Supabase project still needs a manual click-through to fully confirm, since it can't be simulated headlessly.

  **Follow-up (2026-07-27, user-reported):** the manual click-through that couldn't be done at fix-time surfaced exactly the gap flagged as unverified — clicking the real emailed link redirected to the app, but `/reset-password` never appeared. Root cause: `redirectTo: '${origin}/reset-password'` is validated server-side by Supabase against Authentication → URL Configuration → Redirect URLs (exact match unless wildcarded); that specific sub-path was never separately allow-listed (only the bare origin was, for Google OAuth), so Supabase silently dropped the recovery token and fell back to the Site URL instead of ever reaching `/reset-password` — no error surfaced anywhere, matching the reported symptom exactly. **Fixed again:** `redirectTo` changed to the bare origin (`auth.service.ts`) — already virtually guaranteed to be allow-listed, and `AuthContext`'s `PASSWORD_RECOVERY` listener is global, so it doesn't matter which allow-listed page the token lands on. Also added `authLinkError` handling (`auth.context.tsx`/`types/auth.ts`) so a rejected/expired/already-used link surfaces a real message on `LoginPage`/`ResetPasswordPage` instead of silently doing nothing next time. `config.toml`'s local redirect-URL config was also wrong (an `http`/`https` scheme mismatch against `site_url`, so it never matched anything even for local dev) — fixed, with an explicit note that this file does **not** sync to a hosted project's Dashboard settings. See [backend/auth.md §4.3/§4.4](./backend/auth.md) and [frontend/auth.md §4.3](./frontend/auth.md) for the full write-up. **Still requires manual action**: confirm the hosted project's actual deployment origin(s) are present in Supabase Dashboard → Authentication → URL Configuration → Redirect URLs — this cannot be verified or fixed from this codebase alone.

## High

- [x] **No deletion guard on Member.** Plan and Branch both block deletion when referenced by other rows; Member had no equivalent at any layer. Flagged High in [domain-model-review.md](./backend/domain-model-review.md) (2026-07-19).
  **Fixed:** confirmed the product decision with the user (block, not warn/auto-cancel) since it had no prior recorded answer. New `delete-member` Edge Function (`supabase/functions/delete-member/index.ts`) counts non-deleted `subscription_items` referencing the member (`member_id` or `shared_member_id`) and blocks with a 409 "used by X subscription/add-on record(s)" error, otherwise soft-deletes — same shape as `delete-plan`/`delete-branch`, but not admin-only (REQ-MEM-007 is staff/admin). `memberRepository.delete()` now calls this function instead of updating `members` directly; `MemberDetailPage.tsx`'s delete-confirmation dialog surfaces the guard message verbatim (matching the Plan/Branch error-handling convention) and its copy no longer implies a hard delete. Docs updated: [member-management.md](./backend/member-management.md), [domain-model.md:195](./backend/domain-model.md), [edge-functions.md §2](./backend/edge-functions.md), [domain-model-review.md](./backend/domain-model-review.md). Verified via `tsc --noEmit` and a full `vite build`.

- [x] **No indexes on any profiles-referencing FK column.** `created_by`, `changed_by`, `deleted_by`, `handled_by_staff`, `granted_by` had zero supporting indexes anywhere. Same [domain-model-review.md](./backend/domain-model-review.md) High finding.
  **Fixed:** new migration [20260724000000_profiles_fk_indexes.sql](../supabase/migrations/20260724000000_profiles_fk_indexes.sql) adds a plain btree index on every such column across all 10 affected tables (24 indexes total). `user_roles.user_id` didn't need one — already the leading column of its composite primary key. Not applied against a live database in this pass (no local Supabase CLI available in this environment); needs `supabase db push` (or the project's normal migration-deploy path) to actually take effect.

- [x] **Audit Log has no overview screen (REQ-ADMIN-005).** No route, component, or reference to `audit_log` existed anywhere in `frontend/src`.
  **Fixed:** new `/audit-log` screen (`frontend/src/pages/AuditLogPage.tsx` + `.css`), admin-only, reached from the Settings hub's Data Management grid (new card, `frontend/src/pages/SettingsPage.tsx`). Backed by a new `auditLogRepository` (`frontend/src/repositories/audit-log.repository.ts`) — direct RLS-guarded reads via `audit_log_select_admin`, no Edge Function, same pattern as Reports. Filterable by table name (dropdown), record id (text), date range (defaults to current-month-to-date), and changed-by (dropdown, reuses `profileRepository.getAllUsers()`). Capped at 500 rows per filter set with a "narrow your filters" notice if exceeded, since this EAV table's growth is unbounded. Strictly view-only — no edit/delete control anywhere. Docs updated: [screens.md WSCR-14](./frontend/screens.md), [navigation.md](./frontend/navigation.md) (also added the previously-undocumented `/roles` route while in this file), [edge-functions.md §7](./backend/edge-functions.md). Verified via `tsc --noEmit` and a full `vite build` (code-splits into its own chunk).

## Medium

- [ ] **Google OAuth provider config unverified (REQ-AUTH-002).** Frontend is fully wired (`LoginPage.tsx`'s "Continue with Google" → `signInWithOAuth('google')`), but `supabase/config.toml` had no `[auth.external.google]` block at all (only a disabled Apple template).
  **Partially addressed:** added a disabled `[auth.external.google]` scaffold to `config.toml` (mirroring the Apple block) so enabling it later is just filling in `client_id`/`secret`, not writing TOML from scratch. **Cannot be fully fixed from this codebase alone** — it needs an OAuth 2.0 client registered in Google Cloud Console (external account/credentials this environment doesn't have access to) with this project's Supabase Auth callback URL authorized, then either those values filled in here (local dev) or entered directly in the hosted project's Supabase dashboard under Auth → Providers → Google (production — see auth.md §4.4). Left unchecked deliberately; the user needs to complete the external-account steps.

- [x] **`spec/frontend/data-models.md` is entirely stale.** Still described a single `Profile.role` field (actual: `roles: ProfileRole[]` array), a flat 7-field `Member` (actual: 19 fields), and a single-row `Subscription` with embedded plan/dates (actual: header + `SubscriptionItem[]` line items). No `Branch`/`Role` entities documented at all, despite both existing and being used throughout.
  **Fixed:** added a "Superseded — kept for history only" pointer at the top (matching this repo's own convention for other stale docs, e.g. screens.md's WSCR-08/WSCR-12), naming every current authoritative source instead of rewriting 235 lines that would just duplicate `domain-model.md`.

- [x] **`spec/backend/domain-model.md` self-contradicts on `doctor_care_details`.** Line 162 said "Required (app-level, not DB CHECK)"; line 184 documented the very DB CHECK (`chk_doctor_care_details_required`) that already enforces it — the exact fix [domain-model-review.md](./backend/domain-model-review.md)'s Medium finding recommended on 2026-07-19, unapplied 7 days later. Also missing: `Role`/`UserRole` in the ER diagram; `configuration`'s audit columns; the live `profiles_select_self` RLS policy undocumented anywhere.

- [x] **`spec/backend/member-management.md` documents the `member-photos` bucket as public.** It was hardened to private (signed URLs) via `20260723000000_member_photos_private_bucket.sql` — a deliberate, correct security fix — but the spec doc was never updated to match.
  **Fixed:** §8 rewritten to describe the actual private-bucket/signed-URL design, why it changed (predictable object paths + no auth check on a fully public bucket), and the `photo_url`/`photo_thumbnail_url` meaning change (URL → bucket-relative path).

- [x] **`spec/backend/master-data-management.md` / `spec/frontend/master-data-management.md` call Plan/Branch delete guards "deferred."** Both are fully implemented (`delete-plan`/`delete-branch` Edge Functions, "used by X" errors).
  **Fixed:** both docs' intro notes and §5/traceability sections rewritten from "deferred" to "implemented," now also covering the newer `delete-role` and `delete-member` guards for completeness. `screens.md`'s WSCR-08/WSCR-12 superseded-notices updated to match (they also still said "deferred").

- [x] **`/roles` (`ManageRolesPage.tsx`) had zero frontend spec coverage.** Not mentioned in `spec/frontend/navigation.md`, `screens.md`, or `app-shell.md`. `InviteUserPage`'s role selector is also a multi-checkbox array; `navigation.md`/`screens.md` still described a single Admin/Staff radio choice.
  **Fixed:** added `/roles` to `navigation.md`'s route map + access-control table, and a full [WSCR-15](./frontend/screens.md) entry to `screens.md`. Updated WSCR-09/WSCR-10's role-field descriptions from "Admin/Staff chip selector, default Staff" to the actual multi-select-against-the-roles-catalog behavior.

- [x] **`spec/frontend/navigation.md` was internally inconsistent about `RequireAdmin`.** Its prose said "show Access Denied and redirect to `/`"; its own code sample (which the real `RequireAdmin.tsx` correctly matches) only ever renders an inline message and never navigates.
  **Fixed:** prose updated to match the actual (and, arguably, better-UX) inline-message behavior — no redirect. Also fixed the code sample's `currentProfile?.role !== 'admin'` to the real `!currentProfile?.roles.includes('admin')` check, and added the `needsPasswordReset` branch to `RequireAuth`'s sample. ## Low / polish

- [x] Member delete-confirmation copy (`MemberDetailPage.tsx`) reads "will be permanently removed... can't be undone" — true only of the list view; it's actually a soft delete.
  **Fixed** (bundled into the Member deletion guard work above): reworded to "will be removed from the members list, search, and reports. This can't be undone from here."
- [x] REQ-SUB-007's server error message (`create-subscription/index.ts`) cites the plan's numeric ID rather than its name.
  **Fixed:** added `name` to the plan query/`PlanRow` interface and switched every plan-referencing error message in this function (indefinite-item block, quantity/amount/shared-member validation) to cite `plan.name`, not just the one REQ-SUB-007 message — same class of message, same file, trivial to fix consistently.
- [x] `update_subscription_header` RPC unconditionally overwrote `notes` (no coalesce, unlike `payment_mode`) — the calling Edge Function's payload already declares `notes` as optional, so this was reachable today, not just a future risk.
  **Fixed:** new migration [20260725000000_update_subscription_header_notes_fix.sql](../supabase/migrations/20260725000000_update_subscription_header_notes_fix.sql) adds a `p_notes_provided` flag (a plain coalesce can't distinguish "omitted" from "explicitly cleared to null," both look like `NULL`) — `notes` is now only touched when the caller actually included it. `update-subscription/index.ts` updated to pass `payload.notes !== undefined`. No frontend change needed (existing caller already always sends the field, so behavior is unchanged for it). Not applied against a live database in this pass — same caveat as the FK-indexes migration.
- [x] `LoadingView` showed text only, no spinner element, though `app-shell.md` describes "centered spinner + text."
  **Fixed:** added a spinning `RefreshCw` icon (`frontend/src/components/LoadingView.tsx` + new `LoadingView.css`), same spin-animation pattern already used on `LoginPage`/`ManageRolesPage`/`ResetPasswordPage`, respecting `prefers-reduced-motion`.
- [x] Desktop sidebar (`AppShell.css`) is implemented via CSS Grid rather than the literal `position: fixed` `app-shell.md` describes — visually equivalent, just not literally what's written.
  **Fixed (doc):** `app-shell.md §3.3`'s Position row updated to describe the actual Grid-based implementation instead of asking for a specific mechanism the working code doesn't use — the code was fine, the doc was overly prescriptive about *how*, not just *what*.
- [x] No single `frontend/src/types/index.ts` barrel file as `rules.md` prescribed — types are split across 11 well-named files instead. Reasonable deviation, just literal non-compliance.
  **Fixed (doc):** `rules.md` rule 18 updated to describe the actual per-entity-file convention and explicitly endorse it going forward, rather than asking future work to introduce a barrel file for no behavioral benefit.
