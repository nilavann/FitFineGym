# Database Schema & CRUD-Flow Review

> **Historical record.** This review is of the old `public`-schema backend. Its `supabase/migrations/…` and `supabase/tests/…` paths name files of that backend; the old migrations are in git history (`supabase/migrations/` on `master` before the move). The live backend in `supabase/` is the `fitfine` schema.
>
> Two-part audit done 2026-07-27, at explicit request: (1) every table in `supabase/migrations/` checked for required fields, validation constraints, audit-trigger attachment, and soft-delete/hard-delete-prevention; (2) every page in the app traced end-to-end — Create/Retrieve/Edit/Delete — to confirm each UI action hits the right table/columns, with no field silently dropped from an update payload or left stale in the UI after a save. The second part was specifically hunting for a bug class already found once in this codebase: `update_subscription_header` used to unconditionally overwrite `notes` even when a caller's payload omitted it (fixed in `20260725000000_update_subscription_header_notes_fix.sql`, see [audit-findings.md](./audit-findings.md)).
>
> Checklist for tracking — check items off as they're addressed, same convention as [domain-model-review.md](./backend/domain-model-review.md) and [audit-findings.md](./audit-findings.md).

> **Headline:** the original pass found one critical, previously-undetected bug (`audit_row_changes()`'s INSERT branch would have broken every role grant app-wide) plus assorted medium/low findings across ~30 traced CRUD flows and 11 tables — all fixed. A follow-up independent Opus review of those fixes then found that one of them, the indefinite-plan duplicate-check race, was not actually closed by its migration, plus two smaller gaps in the same batch of fixes. Those three are reopened below; everything else this doc originally found has been addressed and is no longer listed here.

## Open

- [ ] **TOCTOU race on the indefinite-plan duplicate check in `create-subscription`.** The "member already has this indefinite plan" check (REQ-SUB-007) runs as a separate `SELECT` before the RPC call, outside the RPC's atomic transaction. Two concurrent checkouts for the same member+indefinite-plan could both pass the check before either inserts, producing two indefinite items for the same plan/member. Narrow window (same admin action, split-second timing), undocumented as an accepted trade-off (unlike the equivalent, explicitly-documented race in `delete-plan`/`delete-branch`'s count-then-update shape).
  **Attempted fix, confirmed incomplete** ([20260801000000_create_subscription_atomic_duplicate_check.sql](../supabase/migrations/20260801000000_create_subscription_atomic_duplicate_check.sql)): moved the check inside `create_subscription_with_items()`, immediately before each item's insert, in the same transaction as the insert — but running in the same transaction as its own insert does not make it atomic *against other transactions*. Supabase/Postgres defaults to READ COMMITTED, and the function takes no lock: no unique/exclusion constraint on `subscription_items(plan_id, member_id/shared_member_id)`, no `SELECT ... FOR UPDATE`, no `pg_advisory_xact_lock`, no `SERIALIZABLE`. Two concurrent callers can each run the `select exists` before the other's insert commits, both see no conflict, both insert — the same race as before, just relocated. Only the sequential (non-concurrent, single-caller-retries) case is actually fixed; that's also the only case a manual re-test would catch. `create-subscription/index.ts` no longer has its own pre-check `SELECT`; it maps the RPC's conflict error to a 409 (line 206), same pattern already used by `update-user`'s last-active-admin checks — this part is fine independent of the race.
  **Found by:** independent Opus review of this file's own "Fixed" changes, 2026-07-27 — verified by reading the migration and grepping the full migration set for any unique index or locking primitive on `subscription_items`; none exists.
  **Real fix, not yet applied:** a `pg_advisory_xact_lock` inside `create_subscription_with_items()`, keyed on `(plan_id, member_id)` (and `shared_member_id` when present), acquired before the `exists` check — serializes concurrent callers for the same plan+member instead of just relocating the check. A partial unique index is the alternative but is complicated by the `member_id`-or-`shared_member_id` OR-logic in the conflict query.
- [ ] **`create-subscription`'s 409-mapping is coupled to the RPC's exact exception text, not a stable error code.** `rpcError.message?.toLowerCase().includes('already has an active indefinite item')` (line 206) matches against the English string raised by `create_subscription_with_items()` (migration line 59). Works today, but if that message is ever reworded, duplicate-indefinite conflicts silently downgrade to an unhandled 500 with nothing to catch the mismatch at build time.
  **Found by:** same independent Opus review, 2026-07-27. Not yet fixed — suggested approach: raise with a dedicated SQLSTATE/custom error code and match `rpcError.code` instead of the message substring.
- [ ] **New blank-name/code CHECK constraints use bare `trim()`, slightly weaker than the client-side validation they backstop.** `trim(name) <> ''` ([20260731000000_name_code_not_blank_checks.sql](../supabase/migrations/20260731000000_name_code_not_blank_checks.sql)) strips spaces only, not tabs/newlines/NBSP, whereas the client's JS `.trim()` strips all whitespace — so a forged `name: "\t"` still passes the DB check. Low severity: these are admin-only, RLS-gated writes, not public-facing input. Also unverified: `ALTER TABLE ADD CONSTRAINT` validates existing rows immediately, so this migration will fail to apply if any current `branches`/`plans`/`roles` row already has a blank/whitespace-only `name`/`code` — not checked against live data in this pass.
  **Found by:** same independent Opus review, 2026-07-27. Not yet fixed.
